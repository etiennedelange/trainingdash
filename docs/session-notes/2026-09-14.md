At least 17 Claude Code sessions touched this repo today, several **overlapping in time**. Multiple digests independently observed:

- **Files changing underfoot**: a session would edit a file, then find it reverted or absent moments later with a clean `git status` — caused by a different concurrent session's work, not a real revert. **Don't assume `git status`/working-tree diffs reflect only your own edits — diff against what you actually intended to touch before committing, and stage/commit only your own files.**

Before relying on chrome-devtools-mcp, check for and kill stale `chrome-devtools-mcp`/Chrome processes and confirm free memory.
- A `.devcontainer/post-create.sh` fix (session d0d5c536) now wires in the existing `install-chrome.sh` script for more reliable Chrome installs on container rebuild — unrelated to the memory issue but adjacent.
- `.mcp.json` chrome-devtools-mcp args were changed in session 31f1867a to match working configs from other repos (`--headless --chromeArg=--no-sandbox --chromeArg=--disable-setuid-sandbox`); **this only takes effect in a brand-new session** — `/mcp` reconnect does not reload `.mcp.json`.

**Fixes (both deployed):**
- **`4a5ff4c`** "fix: batch backfill writes per page and bound run time" — `worker/db/activities.ts` adds `upsertActivityStatement` so a page writes via one `db.batch()` call instead of up to 200 sequential awaits; `worker/sync/backfill.ts` adds a 20s wall-clock budget, saving progress before risking a kill.
- **`1d457a9`** "fix: resume backfill from live traffic, not just the cron" — discovered via Cloudflare's own GraphQL analytics (`workersInvocationsScheduled`) that the account's hourly cron **has never fired even once** — a platform/account-level issue (commonly requires a verified payment method, even on Free plan), not fixable from wrangler/app code. Fix: piggyback backfill continuation on the client's existing `/api/me` polling (every ~4s while importing) — `worker/routes/auth.ts` now fires `runBackfill` via `waitUntil` if not complete and no attempt in the last 15s. Cron trigger left in place as a harmless secondary path.

**Verification:** After deploy + one browser reload triggering `/api/me`, prod D1 jumped from 142 → 516 activities and `sync_state` got its first real row.

**Gotchas:**
- `wrangler dev --remote --test-scheduled` does NOT actually invoke the scheduled handler in `--remote` mode — silently serves only the SPA, a no-op verification path.

### 93ea5873 — 23:05 — PWA update-notification fix (root cause found)
**Goal:** "New version available" prompt wasn't showing after deploys — debug and fix.

**Key changes (landed in commits `dfb616b` and `a7e98e3`):**
- `src/components/UpdatePrompt.tsx` — added a 5-min `setInterval(() => registration.update(), 5*60*1000)` in `onRegisteredSW` since an already-open SPA tab rarely triggers native navigation-based checks.
- **Root cause (the real bug):** Cloudflare Workers' default asset routing 307-redirects `/index.html` → `/`. Workbox's precache installer refuses redirected responses and silently aborts, so the SW never reaches "waiting" state on **any** deploy — no amount of redeploying could have shown the prompt. Fixed via `"html_handling": "none"` in `wrangler.jsonc`.
- UI redesign per user request: `UpdatePrompt` changed from a floating toast to a static sidebar-footer button (above "Log out"); text later changed "Update ready" → "Update available" (`a7e98e3`).

**Gotchas:** Update detection is a native browser byte-diff of `sw.js`; a no-op deploy is byte-identical and legitimately shows no update. Cloudflare's `html_handling` default silently breaks Workbox SW installs — important for any future Workers+PWA precache work.

**Verified live:** index.html → 200 with new etag, all precached assets 200.
